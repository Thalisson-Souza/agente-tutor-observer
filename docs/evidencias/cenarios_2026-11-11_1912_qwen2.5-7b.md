## C1

**Pergunta:** Explique o que é o padrão Observer e qual problema ele resolve.

Claro! Vamos explicar o padrão Observer em camadas.

### Analogia
Imagine que você assina um jornal. Quando o jornal publica notícias, você recebe as atualizações. Você pode cancelar a assinatura a qualquer momento. O jornal é o "Sujeito" e você é o "Observador". O jornal não precisa saber quem são seus leitores, apenas que eles querem receber as notícias.

### Definição
O padrão Observer resolve o problema de manter consistência entre objetos relacionados sem acoplá-los fortemente. Quando um objeto muda, todos os seus dependentes são notificados e atualizados automaticamente. Isso é útil em situações onde vários objetos precisam ser atualizados quando um objeto principal muda.

### Participantes
- **Subject (Sujeito)**: Conhece seus observadores e oferece métodos para anexar e desanexar observadores.
- **Observer (Observador)**: Define uma interface de atualização para objetos que devem ser notificados.
- **ConcreteSubject (Sujeito concreto)**: Armazena o estado de interesse e notifica seus observadores quando o estado muda.
- **ConcreteObserver (Observador concreto)**: Mantém referência ao ConcreteSubject, guarda estado e implementa a interface de atualização.

### Consequências
- **Acoplamento abstrato**: O sujeito só conhece a interface Observer, não as classes concretas.
- **Comunicação broadcast**: Notifica todos os inscritos.
- **Atualizações inesperadas**: Mudanças podem disparar muitas atualizações, o que pode ser custoso e difícil de depurar.

### Quando usar e quando evitar
- **Quando usar**: Quando você precisa manter consistência entre objetos relacionados sem acoplá-los fortemente.
- **Quando evitar**: Quando a notificação não é necessária ou quando o acoplamento entre sujeito e observador é desejável.

## C2

**Pergunta:** Dê um exemplo de aplicação do padrão Observer em Java.

```java
interface Observador { void atualizar(int quantidade); }

interface Sujeito {
    void anexar(Observador o);
    void desanexar(Observador o);
    void notificar();
}

class EstoqueProduto implements Sujeito {          // ConcreteSubject
    private final List<Observador> observadores = new ArrayList<>();
    private int quantidadeEmEstoque;
    public void anexar(Observador o) { observadores.add(o); }
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar() {
        for (Observador o : List.copyOf(observadores)) o.atualizar(quantidadeEmEstoque);
    }
    public void setQuantidadeEmEstoque(int q) { this.quantidadeEmEstoque = q; notificar(); }
}

class NotificadorEmail implements Observador {     // ConcreteObserver
    public void atualizar(int q) { 
        System.out.println("Email enviado sobre estoque: " + q); 
    }
}
```

### Explicação

1. **ConcreteSubject (EstoqueProduto)**: Esta classe implementa a interface `Sujeito` e mantém uma lista de observadores. Quando a quantidade em estoque muda, ela notifica todos os observadores.

2. **Observer (Observador)**: Esta é a interface que define a operação `atualizar`, que será chamada quando houver uma mudança no estado do sujeito.

3. **ConcreteObserver (NotificadorEmail)**: Esta classe implementa a interface `Observador` e define a lógica para o que fazer quando `atualizar` é chamado. Neste exemplo, envia um email informando a nova quantidade em estoque.

### Uso Correto

- **EstoqueProduto** é o sujeito que mantém a quantidade em estoque e notifica os observadores quando a quantidade muda.
- **NotificadorEmail** é um observador que recebe a atualização e envia um email.

## C3

**Pergunta:** Descreva uma situação em que o padrão Observer é a melhor escolha e uma em que ele deveria ser evitado, explicando o porquê.

Claro! Vamos começar com uma analogia simples do cotidiano:

Imagine que você é um jornalista e escreve sobre o clima. Você tem vários leitores que gostam de saber as previsões do tempo. Quando você atualiza a previsão, você quer que todos os seus leitores saibam imediatamente. Mas você não quer que cada leitor tenha que ligar para você para saber quando você atualiza a previsão.

Definição técnica:
O padrão Observer permite que um objeto (o "Subject") mantenha uma lista de observadores (ou dependentes) e notifique-os automaticamente quando seu estado muda.

Participantes e colaborações:
- **Subject**: O objeto que muda seu estado e notifica os observadores.
- **Observer**: O objeto que recebe as notificações do Subject.
- **ConcreteSubject**: A implementação concreta do Subject.
- **ConcreteObserver**: A implementação concreta do Observer.

Consequências:
- Facilita a implementação de notificações de eventos.
- Evita acoplamentos fortes entre os objetos.
- Permite que vários observadores sejam notificados automaticamente.

---

**Uma situação em que o Observer é a melhor escolha:**
Imagine que você está desenvolvendo uma aplicação de previsão do tempo. O modelo meteorológico (Subject) muda seu estado com base em novos dados. Você quer que vários widgets de visualização (Observadores) atualizem automaticamente quando o modelo mudar. Usar o Observer aqui é ótimo porque você não precisa acoplá-los diretamente e pode adicionar novos widgets sem alterar o modelo.

**Uma situação em que o Observer deve ser evitado:**
Imagine que você está criando uma aplicação de controle de estoque. Você tem um único painel de controle (dependente fixo) que precisa ser atualizado sempre que um item do estoque é adicionado ou removido. Neste caso, uma chamada direta ao painel de controle seria mais simples e eficiente do que configurar um Observer.

## C4

**Pergunta:** Como o padrão Observer costuma ser aplicado de forma errada? Dê um exemplo de uso equivocado e explique como corrigir.

```java
import java.util.ArrayList;
import java.util.List;

interface Observer {
    void update(String message);
}

class Subject {
    private List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    public void notifyObservers(String message) {
        for (Observer observer : observers) {
            observer.update(message);
        }
    }
}

class ConcreteObserver implements Observer {
    private String state;

    @Override
    public void update(String message) {
        state = message;
        System.out.println("Observer state updated to: " + state);
    }
}

class ConcreteSubject extends Subject {
    private String state;

    public String getState() {
        return state;
    }

    public void setState(String state) {
        this.state = state;
        notifyObservers(state);
    }
}

public class ObserverExample {
    public static void main(String[] args) {
        ConcreteSubject subject = new ConcreteSubject();
        Observer observer = new ConcreteObserver();

        subject.attach(observer);
        subject.setState("Initial state");

        // Erro: Modificar a lista de observadores durante a notificação
        subject.detach(observer);
        subject.setState("New state");
    }
}
```

### Explicação

**Problema:**
No exemplo acima, o problema ocorre quando o `ConcreteSubject` tenta remover um observador (`observer`) durante a notificação (`notifyObservers`). Isso pode causar um `ConcurrentModificationException` porque a lista de observadores está sendo modificada (`detach`) enquanto está sendo iterada (`notifyObservers`).

**Correção:**
A correção é iterar sobre uma cópia da lista de observadores durante a notificação. Isso pode ser feito usando um `ListIterator` ou criando uma lista temporária com uma cópia dos observadores.

## C5

**Pergunta:** Com qual padrão o Observer é mais confundido? Explique a diferença entre eles e por que essa confusão acontece.

O Observer é mais confundido com o Publish-Subscribe. Ambos envolvem a notificação de múltiplos objetos quando um objeto muda, mas há diferenças cruciais:

1. **Observer** é um padrão de design comportamental que define uma dependência um-para-muitos entre objetos, onde um sujeito (Subject) mantém uma lista de observadores e notifica-os de forma síncrona quando seu estado muda. Os observadores não precisam conhecer o sujeito.

2. **Publish-Subscribe** é um modelo de comunicação assíncrono onde publicadores enviam mensagens a assinantes através de um intermediário (broker ou canal de eventos). Os assinantes não precisam conhecer os publicadores, e a notificação é assíncrona.

A confusão acontece porque o GoF (Gang of Four) menciona o Publish-Subscribe como outro nome do Observer, mas na prática, eles são padrões diferentes com propósitos e implementações distintos.

**Critério Prático para Distinguir:**
- **Observer** mantém uma lista de observadores e notifica-os de forma síncrona. Os observadores são registrados diretamente no sujeito.
- **Publish-Subscribe** usa um intermediário (broker) para notificar assinantes assíncronamente, sem que os assinantes conheçam os publicadores.

## C7

**Pergunta:** O que devo lembrar antes de usar o padrão Observer?

Antes de usar o padrão Observer, você deve lembrar das seguintes coisas:

1. **Relação Um-Para-Muitos**: Existe mesmo uma relação um-para-muitos que muda em tempo de execução? Se a resposta for não, pode não ser necessário Observer.

2. **Tipo de Notificação**: É push ou pull? Defina o que vai na notificação.

3. **Quem e Quando Chamar notify**: Só chame notify quando o estado do sujeito estiver consistente.

4. **Desanexar Observadores**: Cuidado com a desanexação de observadores para evitar vazamento de memória.

5. **Ordem de Notificação**: O código não pode depender da ordem em que os observadores são notificados.

6. **Cascatas e Alterações**: Atente-se para cascatas e observadores que podem alterar o sujeito, pois isso pode causar problemas.

7. **Leveza do update**: O método `update` deve ser leve e eficiente.

8. **Acoplamento Abstrato**: O sujeito deve conhecer apenas a interface Observer, não as classes concretas.

9. **Comunicação Broadcast**: Observer suporta comunicação broadcast, mas isso deve ser usado com cuidado.

10. **Atualizações Inesperadas**: Uma mudança pode disparar uma cascata de atualizações, então é importante garantir que o código não dependa dessa ordem.

11. **Implementação**: Decida entre modelo push ou pull, quem dispara a notificação, e como garantir que o sujeito esteja em estado consistente antes de notificar.

12. **Referências Pendentes**: Cuidado com referências pendentes quando um sujeito é destruído.

13. **Múltiplos Observadores**: Se precisar observar mais de um sujeito, o `update` deve receber o sujeito como parâmetro.

14. **Interesses Específicos**: Considere notificar apenas interesses específicos dos observadores.

15. **ChangeManager**: Pode usar ChangeManager para gerenciar complexidades entre sujeitos e observadores.
