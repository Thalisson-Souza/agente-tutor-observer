## C1

**Pergunta:** Explique o que é o padrão Observer e qual problema ele resolve.

O padrão Observer é um padrão de projeto comportamental que resolve o problema de manter consistência entre objetos relacionados sem acoplá-los fortemente. Ele é também conhecido como "dependentes" ou "publish-subscribe".

**Analogia**: Imagine que você assina um jornal ou um canal de TV. Quando há uma atualização, você recebe notificações imediatas. O sujeito é como a fonte de notícias, o observador é como o leitor do jornal ou o canal de TV, e o sujeito concreto é como a fonte que atualiza a notificação.

**Participantes**:
- **Subject (Sujeito)**: É o objeto que mantém o estado de interesse e notifica seus observadores quando o estado muda.
- **Observer (Observador)**: Define uma interface de atualização (update) para objetos que devem ser notificados. O observador concreto é uma implementação específica do observador.
- **ConcreteSubject (Sujeito concreto)**: Armazena o estado de interesse e notifica seus observadores quando o estado muda.

**Colaborações**:
- O ConcreteSubject chama o método notify() quando o estado muda.
- O notify() chama o update() de cada observador.
- O observador pode consultar o sujeito (getState) para se sincronizar.

**Consequências**:
- **Acoplamento abstrato**: O sujeito só conhece a interface Observer, não as classes concretas.
- **Comunicação broadcast**: Notificações são enviadas a todos os inscritos.
- **Atualizações inesperadas**: Uma mudança pode disparar cascata de atualizações, o que pode ser difícil de depurar.
- **Modelos de comunicação**: O sujeito pode notificar observadores após cada mudança (modelo push) ou observadores podem buscar o que precisam (modelo pull).

**Quando usar**:
- Quando você deseja manter consistência entre objetos relacionados sem acoplá-los fortemente.
- Quando você deseja notificar múltiplos observadores de uma mudança em um sujeito.

**Quando evitar**:
- Quando a comunicação entre objetos é muito complexa ou quando o acoplamento é necessário para a funcionalidade.
- Quando a notificação de mudança é desnecessária ou quando a comunicação é mais simples e eficiente sem o Observer.

## C2

**Pergunta:** Dê um exemplo de aplicação do padrão Observer em Java.

```java
interface Observador {
    void atualizar(String mensagem);
}

interface Sujeito {
    void anexar(Observador o);
    void desanexar(Observador o);
    void notificar();
}

class Notificador implements Sujeito {
    private final List<Observador> observadores = new ArrayList<>();
    private String mensagem;

    public void anexar(Observador o) {
        observadores.add(o);
    }

    public void desanexar(Observador o) {
        observadores.remove(o);
    }

    public void notificar() {
        for (Observador o : observadores) {
            o.atualizar(mensagem);
        }
    }

    public void setMensagem(String m) {
        mensagem = m;
        notificar();
    }
}

class Mensageiro implements Observador {
    public void atualizar(String m) {
        System.out.println("Mensagem recebida: " + m);
    }
}

public class Main {
    public static void main(String[] args) {
        Notificador notificador = new Notificador();
        Mensageiro mensageiro = new Mensageiro();
        notificador.anexar(mensageiro);

        notificador.setMensagem("Olá, mundo!");
    }
}
```

**Explicação:**

- **Notificador (ConcreteSubject):** Representa o objeto que notifica seus observadores. Ele mantém uma lista de observadores e implementa as operações de anexar, desanexar e notificar. Quando o estado do Notificador muda (setMensagem), ele notifica todos os observadores.
- **Mensagem (ConcreteObserver):** Representa o objeto que é notificado e atualizado. Ele implementa a interface Observador e tem um método atualizar para atualizar a sua parte da lógica quando recebe uma notificação.

**Uso incorreto:**

Se o Notificador não implementasse a interface Sujeito, ou se não implementasse as operações anexar, desanexar e notificar, o código não compilaria. Por exemplo, se `Notificador` não implementasse `anexar` e `desanexar`, o código geraria uma exceção devido à falta de implementação dessas operações.

**Correção:**

Para corrigir o uso incorreto, `Notificador` deve implementar a interface `Sujeito` e fornecer as implementações das operações `anexar`, `desanexar` e `notificar`. Além disso, `Mensagem` deve implementar a interface `Observador`.

## C3

**Pergunta:** Descreva uma situação em que o padrão Observer é a melhor escolha e uma em que ele deveria ser evitado, explicando o porquê.

Entendo que o padrão Observer é útil quando há uma necessidade de manter uma relação de dependência entre objetos, onde um objeto (o Subject) muda de estado e precisa notificar outros objetos (os Observers) que dependem dele. Um bom exemplo disso é uma aplicação de gerenciamento de tarefas onde cada tarefa (Subject) pode ser concluída (mudança de estado), e isso deve ser notificado a todos os Observers que estão interessados em atualizações sobre a situação atual das tarefas.

Por outro lado, o Observer deve ser evitado quando há uma única dependência fixa e conhecida. Por exemplo, em uma aplicação de gerenciamento de estoque, onde cada produto (Subject) tem um único observador (um gerente de estoque) que precisa ser atualizado sempre que o estoque muda. Nesse caso, uma chamada direta seria mais simples e eficiente.

## C4

**Pergunta:** Como o padrão Observer costuma ser aplicado de forma errada? Dê um exemplo de uso equivocado e explique como corrigir.

Exemplo de uso equivocado do padrão Observer é quando o observador se desanexa durante a notificação. Isso ocorre porque o observador está percorrendo a lista de observadores dentro do método `atualizar` do sujeito, enquanto o sujeito está percorrendo a lista de observadores dentro do método `notificar`. Isso pode causar um `ConcurrentModificationException`, pois o sujeito está alterando a lista enquanto o observador está percorrenda-la.

**Exemplo de código errado:**

```java
class AlertaUnico implements Observador {
    private final Estacao estacao;
    AlertaUnico(Estacao e) { this.estacao = e; }
    public void atualizar(double t) {
        System.out.println("Alerta: " + t);
        estacao.desanexar(this);   // altera a lista no meio do for abaixo
    }
}

class Estacao {
    private final List<Observador> observadores = new ArrayList<>();
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar(double t) {
        // lança ConcurrentModificationException (ou pula observadores sem avisar)
        for (Observador o : observadores) o.atualizar(t);
    }
}
```

**Exemplo de código correto:**

```java
class AlertaUnico implements Observador {
    private final Estacao estacao;
    AlertaUnico(Estacao e) { this.estacao = e; }
    public void atualizar(double t) {
        System.out.println("Alerta: " + t);
    }
}

class Estacao {
    private final List<Observador> observadores = new ArrayList<>();
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar(double t) {
        // iterar sobre uma cópia da lista para evitar ConcurrentModificationException
        for (Observador o : List.copyOf(observadores)) o.atualizar(t);
    }
}
```

**Explicação:**

O problema do código errado é que o observador `AlertaUnico` está chamando `desanexar(this)` dentro do método `atualizar`, enquanto o sujeito `Estacao` está percorrendo a lista de observadores dentro do método `notificar`. Isso significa que o sujeito está alterando a lista de observadores enquanto o observador está percorrenda-la, o que causa um `ConcurrentModificationException`.

A correção é simples: percorrer a lista de observadores em uma cópia antes de notificar. Isso garante que a lista não será alterada durante a iteração, evitando o `ConcurrentModificationException`.

## C5

**Pergunta:** Com qual padrão o Observer é mais confundido? Explique a diferença entre eles e por que essa confusão acontece.

Com o Observer, o padrão mais confundido é o Publish-Subscribe (ou Publish-Subscribe). Ambos são padrões comportamentais de objetos que abordam a necessidade de notificar vários objetos quando um deles muda de estado. No Observer, o sujeito mantém uma lista de observadores e notifica-os de forma síncrona. Já no Publish-Subscribe, não há conhecimento direto entre o sujeito e os observadores. Há um intermediário (um barramento ou canal de eventos) que centraliza a notificação.

A principal diferença entre eles é que no Observer, o sujeito e seus observadores são conhecidos entre si, enquanto no Publish-Subscribe, nenhum dos lados conhece o outro. No Observer, há uma dependência direta e um-para-muitos, enquanto no Publish-Subscribe, há uma dependência um-para-muitos, mas a notificação é feita através de um intermediário que pode ser um canal de eventos ou um broker.

A confusão acontece porque esses padrões têm nomes semelhantes e podem ser facilmente confundidos, especialmente quando o sujeito e os observadores são conhecidos entre si. No Publish-Subscribe, o termo "Publish-Subscribe" é frequentemente usado, o que pode levar a confusão.

Para distinguir, você pode usar o critério de verificar se há conhecimento direto entre o sujeito e os observadores. Se sim, é o Observer; se não, é o Publish-Subscribe.

## C7

**Pergunta:** O que devo lembrar antes de usar o padrão Observer?

Antes de usar o padrão Observer, você deve lembrar dos seguintes itens do checklist:

1. Existe mesmo uma relação um-para-muitos que muda em tempo de execução? Se há um único dependente fixo, chame-o diretamente.
2. Push ou pull? Defina o que vai na notificação.
3. Quem chama notify e quando? Só com o estado consistente.
4. Como e quando os observadores serão desanexados (evitar vazamento de memória)?
5. O código não pode depender da ordem de notificação.
6. Cuidado com cascatas e com observadores que alteram o sujeito.
7. update deve ser leve.
