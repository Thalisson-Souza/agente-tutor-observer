## C1

**Pergunta:** Explique o que é o padrão Observer e qual problema ele resolve.

Claro! Vamos explicar o padrão Observer de forma simples e didática.

**Analogia:**
Imagine que você assina um jornal. Quando há novidades, você é notificado automaticamente. Você pode assinar ou cancelar a qualquer momento, mas o jornal continua funcionando normalmente.

**Definição Técnica:**
O padrão Observer resolve o problema de manter a consistência entre objetos relacionados sem acoplá-los fortemente. Um objeto chamado Subject pode notificar um conjunto de Observadores quando seu estado muda, e esses Observadores podem então atualizar suas informações.

**Participantes e Colaborações:**
- **Subject**: Conhece os seus Observadores e fornece métodos para adicionar e remover Observadores.
- **Observer**: Define uma interface de atualização para ser notificado.
- **ConcreteSubject**: Armazena o estado de interesse dos Observadores e notifica-os quando o estado muda.
- **ConcreteObserver**: Mantém uma referência para um ConcreteSubject, guarda o estado e implementa a atualização.

**Consequências:**
- O acoplamento entre Subject e Observer é abstrato, permitindo reutilização e independência.
- Suporte a comunicação broadcast, onde a notificação vai para todos os Observadores.
- Possibilidade de atualizações inesperadas, pois os Observadores não sabem dos outros.

**Quando usar e quando evitar:**
- Use quando precisa manter a consistência entre objetos sem acoplá-los fortemente.
- Evite quando a comunicação precisa ser muito específica ou quando o acoplamento entre objetos é necessário.

## C4

**Pergunta:** Como o padrão Observer costuma ser aplicado de forma errada? Dê um exemplo de uso equivocado e explique como corrigir.

```java
// ERRADO: o observador se desanexa enquanto o subject percorre a lista
class Notificador implements Observador {
    private final Notificacao notificacao;
    Notificador(Notificacao n) { this.notificacao = n; }
    public void atualizar(double valor) {
        System.out.println("Notificação: " + valor);
        notificacao.desanexar(this);   // altera a lista no meio do for abaixo
    }
}

class Notificacao {
    private final List<Observador> observadores = new ArrayList<>();
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar(double valor) {
        for (Observador o : observadores) o.atualizar(valor);
    }
}
```

**Explicação:**

O erro ocorre porque o observador `Notificador` se desanexa (`desanexar(this)`) durante a iteração da lista de observadores (`for (Observador o : observadores)`). Isso pode causar um `ConcurrentModificationException`, pois a lista está sendo modificada (`remove`) durante a iteração.

**Correção:**

A correção é fazer a iteração sobre uma cópia da lista de observadores, garantindo que as modificações na lista original não afetem a iteração. A versão corrigida do método `notificar` é:

```java
public void notificar(double valor) {
    for (Observador o : List.copyOf(observadores)) o.atualizar(valor);
}
```

**Pergunta ao estudante:**

Qual é a principal razão para fazer a iteração sobre uma cópia da lista de observadores?

## C5

**Pergunta:** Com qual padrão o Observer é mais confundido? Explique a diferença entre eles e por que essa confusão acontece.

O Observer é mais confundido com o Publish-Subscribe. Ambos envolvem a notificação de múltiplos objetos quando um objeto principal muda, mas há uma diferença crucial. No Observer, o subject conhece os observadores através de uma interface, e os observadores se inscrevem diretamente no subject. Já no Publish-Subscribe, o publicador e o assinante não se conhecem, e a notificação é feita através de um intermediário como um barramento ou broker.

A confusão acontece porque o livro do GOF usa o termo "Publish-Subscribe" como sinônimo do Observer, mas hoje "Publish-Subscribe" costuma designar uma arquitetura com intermediário, onde a entrega é assíncrona e os publicadores e assinantes não se conhecem.

Um critério prático para distinguir é: no Observer, o subject conhece os observadores (só pela interface) e o ConcreteObserver referencia o ConcreteSubject. No Publish-Subscribe com broker, nenhum dos lados conhece o outro.

## C7

**Pergunta:** O que devo lembrar antes de usar o padrão Observer?

Antes de usar o padrão Observer, lembre-se:

1. Existe mesmo uma relação um-para-muitos que muda em tempo de execução? Se há um único dependente fixo, chame-o diretamente.
2. Push ou pull? Defina o que vai na notificação (p. 279).
3. Quem chama Notify e quando? Só com o estado consistente (p. 278).
4. Como e quando os observadores serão desanexados (evitar vazamento de memória)?
5. O código não pode depender da ordem de notificação.
6. Cuidado com cascatas e com observadores que alteram o subject (p. 277).
7. Update deve ser leve.

## E4

**Pergunta:** O Observer é um padrão criacional, né?

A afirmação está errada. O Observer não é um padrão criacional, mas um padrão comportamental. O Observer se preocupa com como objetos se comunicam e dependem um do outro, enquanto os padrões criacionais focam na criação de objetos. Você entende por que o Observer é comportamental e não criacional?
