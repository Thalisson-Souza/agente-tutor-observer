## C1

**Pergunta:** Explique o que é o padrão Observer e qual problema ele resolve.

Claro! Vamos explicar o padrão Observer em camadas.

### Analogia
Imagine que você assina um jornal. Quando há novidades, você recebe as notícias. Você pode cancelar a assinatura a qualquer momento. O jornal é o "Sujeito" que manda as notícias, e você é um "Observador" que recebe as notícias.

### Definição
O padrão Observer resolve o problema de manter consistência entre objetos relacionados sem acoplá-los fortemente. Quando um objeto muda de estado, todos os seus dependentes são notificados e atualizados automaticamente.

### Participantes e Colaboração
- **Subject (Sujeito)**: Conhece seus observadores e oferece interface para anexar e desanexar observadores.
- **Observer (Observador)**: Define a interface de atualização para objetos que devem ser notificados.
- **ConcreteSubject (Sujeito concreto)**: Armazena o estado de interesse e notifica seus observadores quando o estado muda.
- **ConcreteObserver (Observador concreto)**: Mantém referência ao ConcreteSubject, guarda estado e implementa a interface de atualização.

O ConcreteSubject chama `notify()` ao mudar, `notify()` chama `update()` de cada observador, e o observador pode consultar o sujeito para se sincronizar.

### Consequências
- **Acoplamento abstrato**: O sujeito só conhece a interface Observer, não as classes concretas.
- **Comunicação broadcast**: A notificação vai a todos os inscritos, e observadores podem ser adicionados ou removidos em tempo de execução.
- **Atualizações inesperadas**: Mudanças podem disparar cascata de atualizações, o que pode ser custoso e difícil de depurar.

## C2

**Pergunta:** Dê um exemplo de aplicação do padrão Observer em Java.

```java
interface Observador {
    void atualizar(String mensagem);
}

interface Sujeito {
    void anexar(Observador o);
    void desanexar(Observador o);
    void notificar();
}

class Notificador implements Sujeito {                   // ConcreteSubject
    private final List<Observador> observadores = new ArrayList<>();
    private String mensagem;
    public void anexar(Observador o) { observadores.add(o); }
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar() {
        for (Observador o : List.copyOf(observadores)) o.atualizar(mensagem);
    }
    public void setMensagem(String msg) { this.mensagem = msg; notificar(); }
}

class Monitor implements Observador {                    // ConcreteObserver
    public void atualizar(String msg) { 
        System.out.println("Novo monitor: " + msg); 
    }
}
```

### Explicação

1. **ConcreteSubject (Notificador)**: Esta classe implementa a interface `Sujeito` e armazena uma lista de observadores. Quando a mensagem muda, ela notifica todos os observadores.
2. **Observer (Monitor)**: Esta classe implementa a interface `Observador` e define como será atualizada quando houver uma mudança no estado do sujeito.
3. **Interface Sujeito**: Define os métodos `anexar`, `desanexar` e `notificar`.
4. **Interface Observador**: Define o método `atualizar` que será chamado quando houver uma mudança no estado do sujeito.

### Uso Incorreto

Se o estudante tentasse usar `notify()` diretamente no `Notificador` sem passar o `Observador`, isso seria incorreto. `notify()` deve ser chamado com a referência do `Observador` para que o método `atualizar` seja chamado corretamente.

## C3

**Pergunta:** Descreva uma situação em que o padrão Observer é a melhor escolha e uma em que ele deveria ser evitado, explicando o porquê.

Claro! Vamos lá:

**Situção em que o Observer é a melhor escolha:**
Imagine uma aplicação de previsão do tempo. O **Subject** seria a classe que armazena as informações meteorológicas atuais. Os **ConcreteObservers** seriam as interfaces gráficas que exibem essas informações. Quando as condições climáticas mudam, o **Subject** notifica todos os **Observers**, atualizando as interfaces gráficas automaticamente. Isso mantém o código limpo e evita que a classe que armazena as informações meteorológicas saiba detalhadamente como as interfaces são implementadas.

**Situção em que o Observer deve ser evitado:**
Considere um sistema de cadastro onde um usuário pode ter apenas uma janela de cadastro aberta. Se o usuário altera os dados em uma janela, a janela deve atualizar a informação no banco de dados diretamente. Aqui, há um único dependente fixo (a janela de cadastro), então uma chamada direta para atualizar o banco de dados seria mais simples e eficiente. Usar o Observer neste caso seria desnecessário e poderia complicar o código sem razão.

## C4

**Pergunta:** Como o padrão Observer costuma ser aplicado de forma errada? Dê um exemplo de uso equivocado e explique como corrigir.

```java
// ERRADO: o observador faz detach dentro de atualizar(), causando ConcurrentModificationException
class Notificador implements Observador {
    private final Notificacao notificacao;
    Notificador(Notificacao n) { this.notificacao = n; }
    public void atualizar(double t) {
        System.out.println("Notificando: " + t);
        notificacao.desanexar(this);   // altera a lista no meio do for abaixo
    }
}

class Notificacao {
    private final List<Observador> observadores = new ArrayList<>();
    public void desanexar(Observador o) { observadores.remove(o); }
    public void notificar(double t) {
        for (Observador o : observadores) o.atualizar(t);
    }
}

// CORREÇÃO: percorrer uma cópia da lista de observadores
public void notificar(double t) {
    for (Observador o : List.copyOf(observadores)) o.atualizar(t);
}
```

### Explicação

O código errado causa um `ConcurrentModificationException` porque o observador `Notificador` se desanexa (`desanexar(this)`) enquanto o sujeito `Notificacao` percorre a lista de observadores (`for (Observador o : observadores)`). Isso ocorre porque a lista é alterada (`remove`) durante a iteração, violando a regra de que não se deve modificar uma estrutura de dados iterada diretamente.

A correção consiste em percorrer uma cópia da lista de observadores (`List.copyOf(observadores)`), garantindo que nenhuma alteração na lista afete a iteração.

## C5

**Pergunta:** Com qual padrão o Observer é mais confundido? Explique a diferença entre eles e por que essa confusão acontece.

O Observer é mais confundido com o Publish-Subscribe. A diferença principal é que no Observer, o sujeito mantém diretamente a lista de observadores e os notifica de forma síncrona. Já no Publish-Subscribe, há um intermediário (broker ou canal de eventos) e a entrega é assíncrona, além de publicadores e assinantes não se conhecerem.

A confusão acontece porque o GoF cita "Publish-Subscribe" como outro nome do Observer, embora seja um uso impreciso. Um critério prático para distinguir é: no Observer, quem notifica conhece quem é notificado; no Publish-Subscribe, nenhum dos lados conhece o outro, só o intermediário.

Qual desses padrões permite que o sujeito conheça diretamente seus observadores?

## C7

**Pergunta:** O que devo lembrar antes de usar o padrão Observer?

Antes de usar o padrão Observer, lembre-se:

1. Existe mesmo uma relação um-para-muitos que muda em tempo de execução? Se há um único dependente fixo, chame-o diretamente.
2. Push ou pull? Defina o que vai na notificação.
3. Quem chama notify e quando? Só com o estado consistente.
4. Como e quando os observadores serão desanexados (evitar vazamento de memória)?
5. O código não pode depender da ordem de notificação.
6. Cuidado com cascatas e com observadores que alteram o sujeeto.
7. update deve ser leve.
